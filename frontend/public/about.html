The Problem

Why payment support needs an AI teammate

Payment support is mostly a small set of boring, high-volume failures. Agents click through four systems to establish facts that are already in the database. This is exactly the kind of structured, policy-bound work that AI should own.

💸

High-volume, repetitive failures

Payment captured with no order. A refund the customer is entitled to. A settlement that looks like a failed charge. The same 4 failure modes, thousands of times a day, each requiring manual lookup across multiple systems.

🤖

LLMs alone fail in a specific way

A model that answers confidently can also refund ₹50,000 confidently. "The API returned 200" is not the same as "the customer got their order." Standard chatbots have no verification, no policy enforcement, no audit trail.

✅

The right measure of success

The measure is not a good answer. It is a verified customer resolution. Every action must be confirmed against live database state, not just assumed from an API return value.

🔑 Three core commitments

1. The model proposes; the backend disposes

Gemini has no database handle, no URLs, and no tools of its own. It returns one structured JSON decision. Every action it names is routed through a registry that validates, checks role, evaluates policy, executes, and audits in that order. An unauthorised request is refused by code, not by prompt.

2. Nothing is resolved on a claim

After acting, the verification engine re-reads MongoDB and asserts the specific change it expected. Order retry must produce an order in CREATED state. A refund must move the refunded amount. Verification failing escalates the case even if the action reported success.

3. Fallbacks are labelled, never disguised

Gemini, Cognee and n8n can all be down. Each has a local stand-in. The UI shows plainly which one ran: AI MODE: DEMO FALLBACK, MEMORY: LOCAL FALLBACK. The system never claims a service it did not use.

Build Stages

How the project was built, stage by stage

The project evolved through 8 distinct stages, each adding a production layer on top of the previous.

Stage 1 - Foundation

Core Backend + Authentication + Case Engine

Built the entire backend skeleton: Express with Helmet security, bcrypt hashing, JWT auth with role separation (SUPPORT_AGENT vs ADMIN), 10 Mongoose models, and a repeatable seed script that populates a full demo world with realistic Indian payment data.

  • JWT authentication with 12-hour token expiry
  • bcrypt password hashing (cost factor 10)
  • Role-based route guards on every protected endpoint
  • 10 Mongoose models: User, Customer, Merchant, Transaction, Order, SupportCase, Policy, AuditLog, Escalation, Notification
  • Rate limiting: 240 req/min global, 12/10min on login for brute-force protection
// The policy engine: code, not a prompt
const ceiling = 5000; // Rs 5,000 INR
if (amount > ceiling) return { action: 'ESCALATE_TO_HUMAN' }; // No prompt override
Stage 2 - Customer Experience

Customer Portal + Email-to-Case Intake

Added a public-facing customer portal and an email ingestion webhook. Inbound emails from Gmail, Outlook, or n8n automatically create and resolve support cases without agent intervention.

  • Public /customer portal where customers track their own case using a portal access token
  • POST /api/portal/cases creates a case and immediately runs the AI teammate
  • POST /api/intake/email is the production-facing webhook for inbound email-to-case
  • Idempotent messageId deduplication so the same email never creates duplicate cases
  • X-Email-Ingest-Secret header protection on the intake webhook
  • Email Inbox UI for staff to review and action inbound messages
Stage 3 - Autonomous Operations

Risk Intelligence + Anomaly Detection + Action Plans

Added a deterministic multi-factor risk scoring engine combining transaction, customer, merchant, action, and history signals. Added proactive anomaly detection for captured payments with missing orders.

  • 5-factor risk scoring across transaction amount, customer verification, merchant risk, action type, and case history
  • Risk levels: LOW / MEDIUM / HIGH / CRITICAL, each blocking different downstream actions
  • Action-plan persistence: every AI recommendation becomes an ordered execution plan in the DB
  • Proactive merchant anomaly detection scans for payment/order mismatches
  • One-click incident creation from a detected anomaly
  • Live case polling in the Operations UI showing teammate progress in real time
Stage 4 - Control Plane

Admin Panel + Policy Management + Teammate Monitor

Built a full admin control plane with policy configuration, teammate monitoring, and performance dashboards. Admins can tune autonomous refund limits, view AI confidence distributions, and audit every decision.

  • Dynamic policy configuration for refund ceiling, confidence threshold, and max action attempts
  • Teammate activity monitor with real-time resolution and escalation rates
  • Full audit trail filterable by case, event type, actor, and outcome
  • Analytics dashboard showing verified resolutions, autonomous rate, average resolution time
  • Admin-only refund approval flow for escalated cases that executes and verifies on approval
Stage 5 - Real-time Autonomy

n8n Workflow Integration + Live Polling + Notifications

Wired the backend to n8n Cloud webhooks for four core workflows. Added real-time 6-stage progress display so users watch the AI work through investigation, decision, execution, and verification live.

  • 4 n8n workflows: order reconciliation, refund processing, human escalation, customer notification
  • X-ResolveAI-Signature webhook authentication on all n8n calls
  • Local fallback for every n8n workflow so the system works without n8n configured
  • Live 2-second polling during AI resolution so users see the 6-stage pipeline fill in real time
  • Customer notification emails sent via n8n on case resolution
Stage 6 - Multi-Agent Orchestration

Cognee Memory + Knowledge Graph + Verified Resolutions

Integrated Cognee as the AI memory layer. Payment runbooks, refund policies, merchant incident histories, and resolved case write-ups are pushed into a knowledge graph. The AI retrieves relevant context before every decision.

  • Knowledge corpus: payment runbooks, refund policy, escalation policy, merchant history, resolved case write-ups
  • Cognee retrieval uses issue text plus category plus merchant ID as the composite query
  • Retrieved context shown in the case UI with source attribution
  • Local keyword search fallback with honest MEMORY: LOCAL FALLBACK labelling
  • Resolved case summaries written back to Cognee for future retrieval (continuous learning)
  • Demo Center page for rapid hackathon showcasing and judge walkthroughs
Stage 7 - Production Hardening

Security Audit + Error Handling + Request Tracing

Final production pass: tightened security headers, ensured stack traces never reach clients, added request ID tracing, and verified all secrets are server-only and never serialised into responses.

  • Helmet CSP and security headers fully configured
  • All error responses strip internal details before sending to the client
  • Request IDs injected at middleware level and propagated through all audit log entries
  • Zero API keys, DB credentials, or internal URLs in any API response
  • Account enumeration resistance: same error message for wrong password and unknown user
Stage 8 - Hackathon Final

Demo Polish + Seed Data + Walkthrough Scenarios

Final demo preparation: seeded 6 open demo cases and 6 historical cases, polished the 6-stage resolution UI, added quick-fill login buttons, and built the 5-minute hackathon walkthrough flow.

  • 6 open demo cases covering all 4 failure modes (payment/order mismatch, eligible refund, high-value refund, suspicious transaction)
  • 6 historical closed/escalated cases giving the dashboard real metrics on first load
  • Quick-fill login buttons for both demo accounts on the login screen
  • Mode badges on every page showing live vs fallback for AI, memory, and workflows
  • Full test suite covering policy engine, tools, verification, workflow, API routes, and fallback honesty
The AI Loop

The six-stage resolution pipeline

When "Resolve with AI" is pressed, this exact sequence runs. Every stage is persisted to the database and displayed live in the UI as it completes.

01

Investigate

Fetch the customer, transaction, order, and merchant from MongoDB. Build a complete picture of what happened and what the current system state is. No assumptions made.

02

Retrieve Memory

Query Cognee or local keyword search using the issue text plus category plus merchant ID. Retrieve relevant runbooks, past similar cases, and policy excerpts. Show sources in the UI.

03

AI Decision

Send full context to Gemini with a strict JSON schema and responseMimeType application/json. Validate the response with Zod. If Gemini fails or returns invalid JSON, fall through to the rule-based engine.

04

Policy Check

5 rules evaluate in code before any action executes: refund ceiling, confidence threshold, high-risk block, max attempt limit, and suspicious transaction block. A refusal is final and no prompt can override it.

05

Execute Action

Controlled tool registry runs: validate input schema, check caller role, policy gate, execute via DB write plus n8n webhook, write audit record. Gemini never calls a tool directly.

06

Verify State

Re-read MongoDB. Assert the specific change expected: order must be in CREATED state, refunded amount must have moved. If verification fails, escalate even if the action reported success.

Security Model

What the system is structurally incapable of

Security is not enforced by prompts. Every constraint is a code path that runs regardless of what the AI asks for. Gemini is structurally incapable of arbitrary DB access, arbitrary queries, arbitrary URLs, and unrestricted financial actions.

🔐

Authentication

bcrypt hashes (cost 10), JWT with 12h expiry, same error for wrong password and unknown account. Login cannot enumerate users.

🛡️

Authorization

Route-level role guards plus second role check inside the tool registry. The AI caller has role AI and is never ADMIN. It cannot approve its own escalations.

⚖️

Policy Enforcement

5 hard rules in policy/engine.ts. A refund over the ceiling is refused whether the model asks nicely, asks twice, or claims urgency. No prompt override.

✅

Input Validation

Every tool has a Zod schema. Malformed input is rejected before any database access. AI JSON output is also Zod-validated before reaching downstream code.

🔑

Secrets Management

All API keys read from the backend environment only. No key, DB credential, or internal URL is serialised into any API response or reaches the browser bundle.

📋

Audit Logging

Every decision, tool call, policy evaluation, workflow invocation, verification, and human override is stored. Credential-shaped fields are redacted before logging.

🚦

Rate Limiting

240 req/min global API limit. 12 login attempts per 10 minutes per IP. Limits enforced in middleware before any business logic runs.

🚫

Error Handling

Stack traces and driver internals never reach the client. All errors pass through a central handler that strips internal details before sending the response.

🧬

No DB Access for Gemini

Gemini cannot issue MongoDB queries, reach external URLs, or call tools directly. Its only output surface is one validated JSON object the backend may or may not act on.
